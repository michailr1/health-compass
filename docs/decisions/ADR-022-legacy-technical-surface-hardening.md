# ADR-022 — Удалить неиспользуемый legacy technical surface и зафиксировать пустой search_path

Статус: Принято · Дата: 2026-08-27

## Контекст

Первичная миграция `0001` создала `service_metadata`, `audit_events` и
`processing_jobs`. Миграция `0007` затем выдала `health_compass_app`
`SELECT/INSERT/UPDATE/DELETE` на все таблицы схемы. Эти три таблицы не имеют RLS
и больше не входят в актуальную продуктовую модель; их SQLAlchemy-модели
регистрировались только в Alembic metadata.

Две ранние `SECURITY DEFINER` функции magic-link —
`app_issue_email_login_token` и `app_consume_email_login_token` — сохранили
исторический `search_path = health_compass, pg_temp`, тогда как текущий
инвариант для definer-функций требует пустой `search_path` и явную
schema-qualification объектов.

## Решение

1. Миграция `0063` удаляет `service_metadata`, `audit_events` и
   `processing_jobs`, а соответствующие неиспользуемые SQLAlchemy-модели
   удаляются из кода и Alembic registry.
2. Перед удалением миграция проверяет, что все три таблицы пусты. Любая строка
   является stop-condition: upgrade завершается ошибкой до удаления данных.
3. Таблицы удаляются без `CASCADE`. Неожиданная зависимость также является
   stop-condition и требует отдельного разбора.
4. Для обеих magic-link функций `search_path` меняется через `ALTER FUNCTION`
   на пустой. Тела уже используют schema-qualified имена, поэтому изменение не
   меняет бизнес-семантику и не пересоздаёт owner, `row_security` или grants.
5. Downgrade `0063 → 0062` восстанавливает bootstrap-схему, индексы, прежние
   CRUD grants для `health_compass_app` и исторический
   `search_path = health_compass, pg_temp`.

## Следствия

- у application role исчезает незащищённая и неиспользуемая CRUD-поверхность;
- две оставшиеся bootstrap-era definer-функции соответствуют текущему
  `search_path=''` инварианту;
- rollout безопасно останавливается, если фактические production-данные
  расходятся с подтверждённой кодовой моделью;
- Alembic сохраняет единственную линейную голову, а граница `0062 ↔ 0063`
  остаётся реально обратимой.

## Рассмотрено и отвергнуто

**Оставить таблицы и только отозвать grants.** Это уменьшает риск, но сохраняет
мёртвую схему и ложную модель данных. Вариант был бы предпочтителен, если бы
обнаружились реальные потребители или данные; поэтому наличие данных сделано
явным stop-condition.

**Добавить RLS к legacy-таблицам.** Отвергнуто: для неиспользуемых сущностей это
создаёт новую политику владения без продуктового требования и расширяет
поддерживаемую поверхность вместо её сокращения.

**DROP ... CASCADE.** Отвергнуто: новая зависимость не должна удаляться
неявно. Миграция обязана fail closed.

**Пересоздать magic-link функции.** Отвергнуто: тела уже schema-qualified.
`ALTER FUNCTION ... SET search_path=''` минимизирует изменение и сохраняет
остальные security attributes без риска расхождения реализации.

## Инварианты

- `health_compass_app` не получает прямой доступ к незащищённым техническим
  таблицам без явного продуктового назначения и отдельного security design;
- `SECURITY DEFINER` функции используют пустой `search_path` и явно
  квалифицированные объекты;
- security cleanup не удаляет неожиданные production-данные молча;
- production deployment и применение `0063` не входят в это решение и требуют
  отдельного owner-approved rollout/runbook.
