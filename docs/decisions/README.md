# Решения (ADR) — живой реестр

Здесь фиксируется **почему** принято архитектурное или продуктовое решение и
**что было отвергнуто**. Остальные 120+ документов репозитория описывают *что*
и *как*; этот каталог отвечает на вопрос *почему именно так*.

Практика заимствована из параллельного проекта Nails
(`docs/PRACTICES-FROM-NAILS.md`), где записанное решение дважды остановило
выкатку неверного поведения: критерий приёмки противоречил принятому ADR, и
документ показал, что неправ критерий, а не код.

## Отношение к ADR-001…ADR-020 из планировочного комплекта

В репозитории уже есть двадцать ADR:

```text
docs/source-materials/strategic/master-plan-kit/11-adr/ADR-001…ADR-020
```

Они приняты 2026-07-08 на стадии планирования и по правилам
`docs/source-index/SOURCE-REGISTER.md` относятся к **неизменяемым исходным
материалам**: их нельзя редактировать как живой документ. Это и есть причина
завести отдельный каталог — решения, принятые с 2026-07-08 (весь HC-015,
контракты слайсов HC-017, модель неизменяемой коррекции E3, навигационные
решения HC-019), фиксировать было негде.

Правила совместного существования:

- нумерация продолжается сквозной: живые решения начинаются с **ADR-021**;
- ADR-001…020 остаются в силе, пока живое решение явно не заменит их;
- если живое решение меняет исходный ADR, оно обязано назвать его номер и
  причину замены; исходный файл при этом не редактируется;
- при расхождении приоритет источников определяет `PROJECT-PLAN.md` §2:
  код, миграции и тесты выше любого документа.

## Когда решение требует ADR

ADR обязателен, если решение затрагивает:

- схему данных, миграции или контракт БД;
- публичный API или формат ошибок;
- безопасность, RLS, роли, привилегии, обработку секретов;
- медицинскую семантику: что считается подтверждённым фактом, provenance,
  неизменяемость, удаление;
- наблюдаемое пользовательское поведение и продуктовый язык;
- границу «что делает CI, а что приёмка на среде».

Для остального достаточно описания в PR. Не нужно писать ADR ради ADR:
пустой шаблон хуже отсутствия документа.

## Формат

Файл: `ADR-NNN-краткое-имя.md`. Обязательные разделы:

```text
# ADR-NNN — Название

Статус: Принято | Заменено ADR-XXX | Отвергнуто · Дата: YYYY-MM-DD

## Контекст
## Решение
## Следствия
## Рассмотрено и отвергнуто
## Инварианты, которые не ослабляются
```

Два последних раздела — главные. Именно они не дают вернуться к уже закрытому
спору и именно на них ссылается ревью, когда критерий приёмки противоречит
принятому решению.

Раздел «Рассмотрено и отвергнуто» пишется по существу: какая альтернатива,
почему отклонена, при каких новых условиях к ней стоит вернуться.

## Как пользоваться при ревью и постановке задач

- Прежде чем предлагать архитектурное изменение — проверить, нет ли по теме
  принятого решения.
- Если задача требует поведения, противоречащего ADR, — сначала меняется ADR
  (новым решением со статусом «Заменено»), потом код. Не наоборот.
- Если ADR устарел относительно кода — это дефект документации, он
  фиксируется как finding в ревью.
