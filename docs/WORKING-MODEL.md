# Рабочая модель: роли и границы ответственности

Дата: 2026-08-27. Фиксирует фактическое распределение ролей в проекте.

## Три роли

### ChatGPT — архитектор-разработчик, ведущий проект

**Ведёт проект.** Планирует последовательность работ, декомпозирует задачи,
принимает рядовые архитектурные решения и доводит их до результата:

- архитектура и контракты данных;
- весь продуктовый код: backend, frontend, миграции, тесты;
- выбор очередности и объёма слайсов;
- документы реализации, ADR и evidence;
- прогон CI и доведение до зелёного состояния на точном head;
- подготовка runbook-инструкций для Hermes;
- поддержание канонических документов в актуальном состоянии.

**Не выполняет production deployment.** Не принимает решения, требующие
санкции владельца: rollout, включение приёма документов, отказ от принятого
ADR.

### Fable 5 — верхний уровень, подключается по запросу и на контрольных точках

Не ведёт проект и не выдаёт пошаговых заданий. Подключается, когда:

- нужен глобальный архитектурный выбор, затрагивающий несколько контуров
  или меняющий принятый ADR;
- возникла нештатная ситуация: инцидент, деградация, расхождение документов
  и кода, неожиданное поведение production;
- нужна независимая оценка качества: ревизия кода, ревью крупного diff,
  проверка перед rollout;
- исполнитель зашёл в тупик или два решения выглядят равнозначными.

**Не пишет продуктовый код.** Ведёт реестр findings и решений, фиксирует
ревизии. Не выполняет деплой и не трогает production.

### Hermes — VPS-агент

- read-only диагностика production;
- выполнение деплой-runbook из конкретного одобренного SHA;
- backup перед миграцией и проверка его восстановимости;
- smoke-проверки после развёртывания;
- откат по заранее описанным критериям.

**Не принимает архитектурных решений и не меняет продуктовый код.**
Не использует production БД для автоматических тестов. Не выводит секреты.

## Границы, которые нельзя нарушать

- Ни одна роль не выполняет production rollout без явного решения владельца.
- Приём медицинских документов в production не включается изменением
  конфигурации — только reviewed-изменением кода (см. `docs/decisions/ADR-021`).
- Если критерий приёмки противоречит принятому ADR — сначала пересматривается
  ADR, потом код. Не наоборот.
- Расхождение между документом и фактическим кодом — дефект документации,
  фиксируется как finding, а не «подгоняется» кодом.

## Поток задачи

```text
ChatGPT планирует и реализует, гонит CI на точном head, готовит evidence
→ владелец принимает решение о merge
→ владелец принимает отдельное решение о rollout
→ Hermes выполняет runbook и smoke
```

Fable 5 включается в этот поток не на каждом шаге, а по триггерам выше:
перед rollout, при нештатной ситуации, при глобальном архитектурном выборе
и для периодической ревизии качества.

Merge и deployment — **разные** решения. Статусы
`DEFINED / IMPLEMENTED / MERGED / CI VERIFIED / DEPLOYED / OPERATIONALLY ENABLED`
не смешиваются (`PROJECT-PLAN.md` §3).
